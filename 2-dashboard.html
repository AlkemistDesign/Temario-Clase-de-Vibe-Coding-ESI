Context Engineering

En esta tarea vamos a hacer una web tipo dashboard para el estudio. Puedes (y debes) personalizarla todo lo que quieras, añadir funcionalidades, colores, y dejarla a tu gusto. Yo voy a proporcionarte unos prompts básicos con los que experimentar.

Lo interesante frente a la tarea anterior es que vamos a utilizar ingeniería de contexto para refinar lo máximo posible el uso de los LLMs

La ingeniería de contexto consiste en seleccionar, organizar y actualizar la información para que el agente reciba exactamente lo relevante en cada momento, evitando saturar la ventana de contexto.

Arnés (Harness)

El sistema que rodea al modelo y le permite actuar como agente: gestiona el contexto, proporciona herramientas y orquesta la ejecución de tareas.

Guardarraíles

Reglas y controles que limitan las acciones del agente y validan sus resultados (permisos de archivos, aprobaciones y comprobaciones de seguridad).

¿Qué es AGENTS.md?

Es el archivo estándar que los agentes de IA leen automáticamente al iniciar una sesión. Contiene las reglas operativas, el stack tecnológico y los límites del proyecto.

Recomendación: Mantenerlo conciso (entre 30 y 40 líneas) para no desperdiciar tokens.

AGENTS.md

## Rol

Actúa como desarrollador frontend senior que escribe código simple, claro y fácil de entender para alguien que está empezando a programar.

## Contexto

Quiero crear desde cero "Diario de Estudio", una web para registrar mis sesiones de estudio y motivarme viendo mi racha de días seguidos estudiando. Esta es la primera versión y tiene que ser muy simple. La web se construirá poco a poco, así que ahora solo necesito una base limpia que funcione a la primera.

## Tarea

Crea la web con estas funcionalidades:

1. Un formulario para registrar una sesión con:

- Fecha (por defecto hoy, pero editable para poder apuntar días anteriores)

- Tema (texto, obligatorio)

- Minutos (número mayor que 0, obligatorio)

2. La racha actual en grande, con un 🔥.

3. La lista de sesiones, de la más reciente a la más antigua.

4. Los datos guardados en localStorage para que no se pierdan al recargar.

## Restricciones y reglas

Racha:

- Un día cuenta si tiene al menos una sesión.

- La racha son los días consecutivos con sesión que terminan hoy.

- Si hoy todavía no he estudiado pero ayer sí, la racha sigue viva: no se rompe hasta que termina el día.

- Usa siempre la fecha local del usuario, nunca UTC.

Técnicas:

- HTML, CSS y JavaScript, sin frameworks, sin librerías y sin compilar nada.

- Solo tres archivos: index.html, styles.css y app.js.

- Tiene que funcionar abriendo index.html con doble clic, sin servidor ni instalación.

- No añadas nada que no aparezca en este mensaje.

- Diseño limpio y moderno, que se vea bien en el móvil.

- Todos los textos de la interfaz en español.

## Formato de salida

1. Crea los tres archivos directamente en la carpeta del proyecto.

2. Al terminar, responde con:

- Un resumen de 3-4 líneas de lo que has creado.

- Los pasos para probarlo.

- Cualquier decisión que hayas tomado por tu cuenta y que yo deba revisar.

DESIGN.md

¿Cómo definir DESIGN.md?

En mi experiencia la mejor forma de escribir un DESIGN.md es usar un prompt que te haga preguntas y te ayude a definirlo.

Recurso externo

Consulta más información y especificaciones de diseño en:

https://designmd.ai/
Prompt para generar un DESIGN.md

Actúa como un Lead UX/UI Designer y Arquitecto Frontend. Mi objetivo es definir y documentar de forma exhaustiva el sistema de diseño de un nuevo proyecto web y generar un archivo `DESIGN.md` altamente técnico y estructurado.

Tienes un archivo `AGENTS.md` con la definición del proyecto. Úsalo como contexto para entender el producto.

Para lograr mi objetivo, necesito que me entrevistes para recopilar la información. NO generes el documento `DESIGN.md` todavía. Sigue estrictamente este proceso paso a paso, haciéndome preguntas divididas en 5 fases. Hazme solo las preguntas de una fase, espera mis respuestas y luego pasa a la siguiente.

**Fases de la entrevista:**

1. **Filosofía Visual, Principios y Normas de Accesibilidad (A11Y):**

- ¿Cuál es el enfoque visual principal de la interfaz? (ej. Minimalismo funcional, diseño corporativo, UI tipo editor/terminal).

- ¿Qué normas de accesibilidad (A11Y) debemos cumplir estrictamente? (ej. Nivel WCAG AA o AAA, ratios de contraste, soporte para lectores de pantalla/ARIA, y manejo de animaciones con `prefers-reduced-motion`).

2. **Metodología de Color y Tipografía:**

- ¿Qué sistema o metodología de color utilizaremos como base? (ej. Paleta tonal MD3, Tailwind colors, Radix UI).

- ¿Cuáles serán los colores principales (Primario, Acento) y cómo estructuraremos la inversión semántica para el Modo Claro / Modo Oscuro?

- ¿Qué estilo tipográfico buscamos? (Fuente general, fuente monoespaciada para código/datos y escala tipográfica).

3. **Espaciado, Layout y Arquitectura de Navegación:**

- ¿Usaremos un sistema de espaciado base de 4px/8px? ¿Qué estilo de bordes (border-radius) y sombras (elevaciones) prefieres?

- ¿Cómo será la arquitectura de navegación general? (ej. Navbar superior fija, Sidebar colapsable, controles inferiores).

- ¿Qué comportamiento y adaptaciones mobile-first (< 768px) debemos prever?

4. **Elementos Base y Estados de Interacción (Core UI):**

- ¿Qué jerarquía de botones necesitamos (Primario, Secundario, Outline, Ghost/Texto)?

- ¿Cómo deben comportarse y verse visualmente los estados de interacción (hover, active, focus-ring para accesibilidad, disabled, loading)?

- ¿Hay alguna directriz particular para los inputs de formularios base?

5. **Componentes Específicos y Necesidades del Proyecto (Basado en el AGENTS.md):**

- *Instrucción para la IA:* Basándote en la información del proyecto/AGENTS.md, formula de 2 a 4 preguntas sobre **componentes o widgets exclusivos y complejos** que requerirá este proyecto en particular (por ejemplo: si es una plataforma educativa, pregunta por bloques de código o quizzes; si es un SaaS, pregunta por tablas de datos complejas o dashboards).

- ¿Cómo debemos estilizar los enlaces de acción externa o recursos destacados?

**Reglas de la entrevista:**

- Haz preguntas claras y fáciles de responder.

- Ofréceme 2 o 3 opciones o ejemplos de respuesta.

- Una vez completadas las 5 fases, confirma que tienes todo y genera el archivo `DESIGN.md` completo en un bloque de código listo para copiar. El documento final DEBE incluir: normas de accesibilidad, tablas de tokens claro/oscuro, jerarquía tipográfica, arquitectura del layout, anatomía de botones/estados, y los componentes específicos del proyecto con ejemplos de código (HTML/Tailwind).

Comienza confirmando que has leído el contexto del proyecto (si ya lo tienes) o pídeme que te lo comparta, preséntate brevemente y lanza las preguntas de la Fase 1.

Ahora debemos añadir lo siguiente al AGENTS.md:

AGENTS.md

- Consultar DESIGN.md para todas las decisiones tipográficas, paleta de colores, márgenes, sombras y detalles visuales específicos.

Modo Plan

Planificar antes de actuar

Shift + TAB

El modo plan permite al agente analizar una tarea, consultar el proyecto y proponer los pasos antes de ejecutarlos. Sirve para aclarar requisitos, detectar riesgos y revisar el enfoque contigo antes de modificar archivos.

Cuándo usar el Modo Plan
  • • Tareas grandes o nuevos módulos
  • • Refactorizaciones complejas
  • • Supervisión de arquitectura y estrategia
Cuándo NO usarlo (Modo Build directo)
  • • Tareas pequeñas o puntuales
  • • Correcciones obvias de sintaxis o estilos
  • • Prototipado rápido desechable

Diferencia entre Workflow y Skill

Tanto los Workflows como los Skills sirven para automatizar y estandarizar tareas. La diferencia principal radica en cómo y quién puede usarlos.

Comparativa

Característica Workflow (Flujo de trabajo) Skill (Habilidad)
Definición Una secuencia lineal de pasos fijos y ordenados. Un paquete de capacidades y conocimientos permanentes.
Invocación Se invoca manualmente en el cajón de prompts empleando comandos específicos Autónoma por el agente o explícita.
Estructura Un único archivo (habitualmente Markdown o YAML). Un directorio bundled (SKILL.md + scripts + referencias).
NOTA: Antigravity 2.0 está migrando los flujos de trabajo hacia un modelo basado principalmente en Skills.

Comandos Personalizados (Workflows)

Un workflow es un prompt reutilizable que ejecutas escribiendo /nombre_comando. Permite repetir tareas habituales sin volver a escribir las instrucciones desde cero.

Pasos para crear un comando en Antigravity IDE:

  1. En el chat de la derecha le damos a los 3 puntos.
  2. Entramos en Customization.
  3. Vamos a la pestaña de Workflows.
  4. Aquí nos salen todos los que tenemos creados y dos botones para añadir:
    • Global: Estará accesible desde cualquier proyecto
    • Workspace: Solo para el repositorio que tenemos abierto
  5. Una vez le damos a crear nos pregunta el nombre y nos genera el archivo.
  6. Añade el encabezado con la descripción y las instrucciones del prompt.

Agent Skills (Habilidades del Agente)

Un Skill es un conjunto de instrucciones reutilizables que enseña al agente cómo realizar una tarea concreta. El agente puede cargar las instrucciones completas cuando las necesita.

Ubicaciones de las Skills

Local (Espacio de trabajo)

Se guardan en la raíz de tu proyecto dentro de la carpeta .agent/skills/{nombre-de-la-skill}/SKILL.md (o .agents/skills/). Tienen la prioridad más alta.

Global

Se almacenan en el directorio de configuración del usuario en tu equipo, habitualmente en vuestro-usuario/.gemini/config/skills/. Estas están disponibles para cualquier proyecto.

Ejemplo Práctico: Skill de Manejo de Fechas

Las fechas y zonas horarias son una fuente común de errores en aplicaciones web. Una skill especializada previene que el modelo use métodos problemáticos como toISOString() en UTC.

Archivo: .agents/skills/local-dates/SKILL.md Habilidad de fechas
SKILL.md (local-dates) 
---
name: local-dates
description: Úsala siempre que escribas, modifiques o revises código que trabaje con fechas, días, semanas o rachas en el Diario de Estudio.
---

# Fechas locales en el Diario de Estudio

Las fechas son la mayor fuente de bugs de este proyecto. Sigue esta guía siempre que toques código con fechas.

## Reglas
- Las fechas se guardan como texto "AAAA-MM-DD" en la zona horaria local del usuario.
- Para obtener el día de hoy, construye el texto con getFullYear(), getMonth() + 1 y getDate(), rellenando con ceros.
- Para convertir "AAAA-MM-DD" en fecha, usa new Date(año, mes - 1, día). Nunca new Date("AAAA-MM-DD"): se interpreta en UTC.
- Nunca uses toISOString() para obtener el día: devuelve la fecha en UTC.
- Para sumar o restar días, usa setDate(getDate() ± n), nunca milisegundos (24 h no siempre es un día por los cambios de hora).
- Reutiliza las funciones de fechas que ya existan en app.js antes de crear otras nuevas.

## Checklist de revisión
- [ ] ¿Algún toISOString() o new Date("AAAA-MM-DD")?
- [ ] ¿Algún cálculo con 86400000 milisegundos?
- [ ] ¿Qué pasa con una sesión registrada a las 00:30?
- [ ] ¿Qué pasa el día del cambio de hora (último domingo de marzo y de octubre)?
- [ ] ¿Se ignoran las fechas futuras donde corresponde?

Model Context Protocol (MCP)

MCP es un protocolo abierto estandarizado que permite conectar de manera segura al modelo de lenguaje con herramientas locales, navegadores web, bases de datos y APIs externas.

Cómo añadir un servidor MCP a tu proyecto:

  1. Dale a los tres puntitos en el chat del agente
  2. Selecciona MCP SERVERS
  3. Busca el MCP que quieres instalar

Si el MCP no sale en la lista

Edita o crea el archivo mcp_config.json en la ruta: C:\Users\TuUsuario\.gemini\config\mcp_config.json

También puedes añadirlo dentro de tu proyecto en: plugins/nombre_plugin/mcp_config.json
