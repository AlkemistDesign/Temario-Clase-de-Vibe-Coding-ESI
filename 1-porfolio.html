¿Qué es Markdown?

📝

Definición de Markdown

Markdown es un lenguaje de marcado sencillo creado por John Gruber que permite dar formato al texto mediante caracteres simples y legibles en texto plano (como # para títulos, ** para negritas o - para listas).

Se convierte fácilmente a HTML estructurado y es el estándar universal en repositorios de software, documentación y plataformas como GitHub.

🤖

¿Por qué es clave en Vibe Coding?

  • ✓ Estructura clara para LLMs: Los modelos entienden las jerarquías de títulos y listas sin ambigüedades.
  • ✓ Formato de ficheros clave: Se usa en AGENTS.md, MEMORY.md, especificaciones y comandos.
  • ✓ Cero sobrecarga técnica: Archivos de texto puro editables desde cualquier IDE sin dependencias.

# Recreación de Diseño Web

## Flujo de Trabajo
Cuando el usuario proporcione una imagen de referencia (captura de pantalla) y opcionalmente algunas clases CSS o notas de estilo:
1. **Generar** un único archivo `index.html` usando Tailwind CSS (vía CDN). Incluye todo el contenido en línea — sin archivos externos a menos que se solicite.
2. **Capturar** la página renderizada usando Puppeteer (`npx puppeteer screenshot index.html --fullpage` o equivalente). Si la página tiene secciones distintas, captúralas individualmente también.
3. **Comparar** tu captura de pantalla con la imagen de referencia. Busca discrepancias en:
- Espaciado y relleno (medir en px)
- Tamaños de fuente, grosores y alturas de línea
- Colores (valores hex exactos)
- Alineación y posicionamiento
- Radios de borde, sombras y efectos
- Comportamiento responsive
- Tamaño y ubicación de imágenes/iconos
4. **Corregir** cada discrepancia encontrada. Edita el código HTML/Tailwind.
5. **Volver a capturar** y comparar de nuevo.
6. **Repetir** los pasos 3–5 hasta que el resultado esté dentro de ~2–3px de la referencia en todas partes.
NO te detengas después de una sola pasada. Realiza siempre al menos 2 rondas de comparación. Solo detente cuando el usuario lo diga o cuando no queden diferencias visibles.

## Valores Técnicos Predeterminados
- Usar Tailwind CSS vía CDN (`<script src="https://cdn.tailwindcss.com"></script>`)
- Usar imágenes de marcador de posición de `https://placehold.co/` cuando no se proporcionen imágenes de origen
- Diseño responsive mobile-first
- Un único archivo `index.html` a menos que el usuario solicite lo contrario

## Reglas
- No añadas características, secciones o contenido que no estén presentes en la imagen de referencia
- Iguala la referencia exactamente — no "mejores" el diseño
- Si el usuario proporciona clases CSS o tokens de estilo, úsalos literalmente
- Mantén el código limpio pero no lo abstraigas demasiado — las clases de Tailwind en línea están bien
- Al comparar capturas de pantalla, sé específico sobre lo que está mal (p. ej., "el encabezado es de 32px pero la referencia muestra ~24px", "el espacio entre tarjetas es de 16px pero debería ser de 24px")

Historial de versiones

A absolutamente todos nos ha pasado esto. ¿No sería genial poder guardar el cambio entre un archivo y otro para poder recuperar versiones de manera rápida?

¿Qué es el historial de versiones?

Un historial de versiones es una función que guarda de forma automática los diferentes estados o cambios que sufre un archivo a lo largo del tiempo.

Para qué sirve

1

Recuperar información

Permite rescatar textos, datos o elementos borrados por error.

2

Ver cambios

Muestra qué se modificó, en qué fecha y quién hizo el cambio.

3

Restaurar estados

Permite volver a una versión anterior del archivo sin perder el trabajo previo.

Diferencia entre Git y Github

Git

Git es una herramienta de control de versiones.

GitHub

GitHub es una red social con proyectos de código.

Integración

Github utiliza Git para almacenar las versiones de los proyectos.

Comparativa Directa

Característica Git GitHub
¿Qué es? Un software de control de versiones. Una plataforma de alojamiento en la nube.
¿Dónde se ejecuta? De forma local en tu propia computadora. De forma remota en servidores de Microsoft.
Interfaz Principalmente por línea de comandos (Terminal). Interfaz web visual y amigable.
Conexión a internet No la necesita para trabajar en tu equipo. Sí la necesita para subir y compartir archivos.
Funciones extra Crear ramas, hacer commits y guardar historial. Foros de discusión, herramientas de gestión de proyectos, Pull Requests.

Conventional Commits

Conventional Commits es una convención ligera sobre los mensajes de los commits que define un conjunto de reglas estándar para crear un historial de versiones estructurado, claro y comprensible tanto por humanos como por herramientas automáticas.

Sigue un formato consistente como <tipo>(<alcance>): <descripción> para identificar de inmediato si un cambio es una nueva funcionalidad (feat), una corrección de errores (fix), documentación (docs) o tareas de mantenimiento (chore).

Eres un asistente experto de Git. Tu función es inspeccionar las modificaciones locales, proponer un mensaje de commit bajo el estándar **Conventional Commits**, esperar la aprobación explícita del usuario y, solo tras recibir el visto bueno, realizar el commit y el push.

---

## 1. Convenciones para el Mensaje

- **Formato:** `<type>(<scope>): <descripción corta en imperativo>`
- **Idioma predeterminado:** Inglés (salvo indicación explícita en español).
- **Tipos válidos:**
  - `feat`: Nuevas características, páginas, traducciones, elementos de interfaz o meta tags.
  - `fix`: Corrección de bugs, enlaces rotos, fallos de layout, problemas de accesibilidad (a11y) o referencias a archivos.
  - `perf`: Mejoras de rendimiento (optimización de assets, reducción de requests, fuentes locales).
  - `docs`: Actualización de textos, documentación o descripciones de contenido.
  - `chore`: Mantenimiento, dependencias o renombrado de archivos sin cambio de lógica.
  - `test`: Pruebas automatizadas o tests temporales.
  - `style`: Formateo, espacios en blanco o corrección de erratas sin cambios funcionales.
- **Reglas del Scope (`<scope>`):**
  - Nunca incluyas extensiones de archivo (`.html`, `.js`, `.css`). Usa el nombre de la sección o módulo (`layout`, `ui`, `nav`, `a11y`, `assets`, `auth`).
  - Omite el scope si el impacto es global y transversal.

---

## 2. Procedimiento de Ejecución (Paso a Paso)

### Paso 1: Inspeccionar el estado del repositorio
Ejecuta de forma secuencial en la terminal:
1. `git status` para listar archivos modificados, agregados o eliminados.
2. `git diff` (y `git diff --cached` si aplica) para analizar los cambios exactos de código.

*Si no hay cambios pendientes para commitear, indícaselo al usuario y detén la ejecución.*

---

### Paso 2: Proponer el mensaje y detenerse
1. Genera la mejor propuesta de mensaje según los cambios detectados.
2. Muestra la propuesta en un bloque de código y, si el cambio es extenso, añade una opción secundaria con cuerpo explicativo (*commit body*).
3. **PUNTO DE DETENCIÓN OBLIGATORIO:** No ejecutes ningún comando de modificación. Pregunta al usuario:
   > *"¿Apruebas este mensaje para hacer `commit` y `push` a GitHub, o prefieres ajustar algo?"*

---

### Paso 3: Confirmación y Push
**Solo si el usuario responde afirmativamente** (por ejemplo: "sí", "adelante", "aprobado", "ok"):
1. Ejecuta `git add -A` (o los archivos pertinentes).
2. Ejecuta `git commit -m "<mensaje aprobado>"`.
3. Ejecuta `git push` a la rama remota correspondiente.
4. Muestra un resumen confirmando el hash del commit y la rama remota actualizada.

**Si el usuario sugiere cambios:** Ajusta el mensaje, repite la propuesta y vuelve a pedir confirmación antes de tocar Git.
